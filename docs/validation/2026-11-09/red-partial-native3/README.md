# 第二组原生3次重复对照

2026-11-09，用户同意[首组变灰排查](../red-partial-stage4/README.md)提出的同阶段3次重复后，使用隔离worktree中的`red_partial_native3`执行一次试验。Arduino上传Hash校验通过；唯一目标端口`/dev/cu.usbmodem2101`，原引脚、3.3V、4MHz SPI、FQBN及4MB分区不变，不写OTP、不改电压、不清NVS。

- 原厂基准全刷20651ms，BUSY正常结束；233字节原生波形两次读回一致，且与首组逐字节一致。
- 相对首组候选，仅偏移0/56/112/168从`01`改为`03`，其余223字节相同；运行前、写入后读回均通过，6字节原生结束／电压参数一致。
- 名义174帧/3480ms，RED表VSH2阶段累计102帧/2040ms。一次Mode 1/C7激活实际3748ms，观察到BUSY拉高并回低，无超时，没有自动重试。
- 用户实屏反馈：“左边的残留更浅了, 中间更深了还没有变红”。因此延长同阶段驱动能够改变灰度和擦除程度，但没有形成目标红色。右侧红块及整体背景尚无明确反馈，不记为通过。

## 结论与进一步排查

本轮否定了“只把该阶段恢复为3次就可以形成红色”的具体方案，不能据此证明红色局刷不可能。前次“更可能只是时间太短”的解释不足；完整波形中的预处理／黑红分离，以及图像编码／驱动模式，都还需要区分。

进一步审查本机GxEPD2 1.6.9原厂全刷路径，发现新的待验证差异：

1. `GxEPD2_3C.h::drawPixel`先将黑白缓存位置1，绘制红色时只把颜色缓存对应位置0。
2. 该类把两个缓存直接传给`epd2.writeImage`；`GxEPD2_420c_GDEY042Z98.cpp::writeImage`原样发送黑白缓存到0x24，反相发送颜色缓存到0x26。
3. 因此已在本实物显示红色的正式路径，最终为`R/BW=11`；两个实验都使用`10`。SSD1683兼容手册列出`10`为红色，但没有给出两者在当前实物上的等价性证据。

这不等于已定位唯一根因，但说明首轮“原厂路径支持本实验编码”的判断过早。下一轮应优先仅把中间目标的编码对齐正式路径，保持已测的阶段与时长；若仍灰，再对照完整红色阶段链路。本次未实施第三组，也未提高电压或继续增加驱动次数。

源代码核对参考：[GxEPD2_3C.h](https://github.com/ZinggJM/GxEPD2/blob/master/src/GxEPD2_3C.h)、[GDEY042Z98驱动](https://github.com/ZinggJM/GxEPD2/blob/master/src/gdey3c/GxEPD2_420c_GDEY042Z98.cpp)。本次结论来自本机实际安装的1.6.9版本；上游未来变化不替代此次版本证据。图像RAM尚未回读，实际驱动电压也未测量，不排除其他因素。
